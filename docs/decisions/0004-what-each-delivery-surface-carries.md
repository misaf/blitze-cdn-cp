# What each delivery surface carries

Status: accepted; documents the design in `capabilities.dns.domain.patch`,
`capabilities.dns.service`, and `tests/contract/test_delivery_parity.py`.

## Context

The CLI and the HTTP API are both thin adapters over the same services, and
they were kept in step by nobody. `tests/contract/frozen/cli.txt` and
`http.txt` freeze the two surfaces independently; both are regenerated by the
same `just refreeze`, so a route added without its command and a command added
without its route each arrive as an ordinary-looking diff.

Two things had already gone wrong under that, and neither was noticed by a
test.

The first is a gap. `POST /v1/hosts/{name}/certificate/upload` and
`.../request` existed with no command beside them, so an operator at a terminal
could renew every certificate in the fleet but not install one they held, or
issue one for a single site whose preflight had just started passing.

The second is a hole. `certificate_mode` and its two paths are on `DomainPatch`
because `_assert_patch_covers_zone` requires every zone field to be patchable —
a rule written for settings an operator owns, applied to three fields the
*issuer* owns. `HostService.activate_managed_certificate` derives those paths
from a derived host's name, and one zone derives several hosts: its own, and
one per rule that claims a hostname. So a zone-level patch naming a
controller-managed mode cannot say which host the paths belong to, and `Domain`
cannot check it — the comment on `validate_certificate_pair` says exactly this
and stops there. `CdnSite` does check it, far downstream, where the only thing
left to do is refuse to build the host; `derive_hosts` then drops it rather
than raising, because a derivation cannot fail on state that is merely
incomplete. The zone's hostnames stop being served, and nothing says so until
somebody runs `blitzecdn validate`.

## Decision

**The surfaces are not required to match, but every asymmetry is declared.**
`tests/contract/test_delivery_parity.py` holds one row per operation naming the
command, the route, and — for a row that has only one of the two — why. The map
is exhaustive by construction: a command or route in neither column fails with
the row it needs. The test does not ask the surfaces to be symmetric, because
they should not be. `config set` edits a `.env` on the control-plane host and
`GET /metrics` answers a scrape; what was missing was never symmetry, it was
the record of who decided.

Fifteen `domain` commands map to one `PATCH /v1/domains/{domain}`, and that
stays. The CLI names the intent an operator has; the API takes the patch a
client already computed. Collapsing the CLI to one `--set` would trade a
discoverable `--help` for a field list, and splitting the route into fifteen
would cost fifteen round trips and the atomic update.

**`cert upload` and `cert request` close the gap.** `upload` takes two paths
rather than the route's multipart body: that is the shape the material is
already in on an operator's machine, and reading the file keeps a private key
out of the argument vector.

**An issuer-owned certificate mode is refused at the operator's entry points,
not in the model.** `CertificateMode.issuer_owned` is the one statement of
which modes those are — `uploaded` and `requested` — and
`reject_issuer_owned_certificate` is asked by `DnsService.update_domain` and by
`RuleService.create_rule`/`update_rule`.

The placement is the whole decision, and the two rejected alternatives are
rejected for concrete reasons rather than taste:

- **Not on `DomainPatch`.** Both callers speak in patches, so the validator
  looks like it belongs there. But `activate_managed_certificate` records a
  rule's issued certificate *as* an overrides mapping, and that mapping is the
  one that legitimately carries `requested`.
- **Not in `Rule._validate_overrides`.** This was tried and reverted during
  implementation. That function runs on every rule the store rehydrates as well
  as on every rule an operator writes, so refusing the mode there makes the
  issuer's own rules unreadable and takes `list_rules` down for the whole
  fleet. `tests/capabilities/dns/test_zone_rules.py` holds that regression
  down by name.

What is being checked is not the value but who is setting it, and only the
entry point knows. The three fields stay patchable, because `existing` — TLS
material somebody else put on the box, which the control plane neither issues
nor renews — is the operator's to set.

## Consequences

A new route or command must be classified before it can be merged. That is one
row of work, and it is the point: the row is where an author has to say out
loud whether the other surface should have grown too.

`seed_site` now seeds a controller-managed certificate the way a deployment
reaches one — operator policy, then `activate_managed_certificate`, then the
TLS mode that only becomes legal once a certificate exists. It previously did
it in a single `update_domain`, which the guard refuses. That fixture was
fabricating a state no deployment can reach, so the sequence is the more
faithful one regardless of the guard.

The CLI surface gained two lines and lost none, which is additive; see
COMPATIBILITY.md for what that obliges.

`certificate_mode` remains on `DomainPatch`, so `_assert_patch_covers_zone` is
untouched. A future field that is genuinely nobody's to patch would need that
assertion to grow an exemption set, and this decision is not that.
